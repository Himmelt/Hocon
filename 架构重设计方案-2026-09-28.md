## 1. 项目意图（方案的第一性依据）

从 `README.md` 与现有代码归纳出的三条意图，本方案的所有取舍都以它们为准绳：

| #  | 意图                                                                                  | 证据                                                                                     |
| -- | ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| I1 | **轻量、零依赖、只用 JDK 8**                                                                 | `README` 第 25 行"没有其他依赖项"；`build.gradle` 无任何 `dependencies`；`sourceCompatibility = 1.8` |
| I2 | **面向"人可读可写"的配置文件**：注释要紧挨配置项保留，格式要能手工编辑                                              | 注释/文件头（`heads`）是一等公民；`keepComments` 开关；README 大篇幅讲缩进与手写                                |
| I3 | **不止读文本，还要把文本绑到 Java 对象**：`@Setting` 注解字段 ↔ 结点树双向映射（含静态字段、容器、枚举、自定义序列化器），并支持注释本地化翻译 | `Sett`<u>`ing`/`modify`/`extract`/`TypeSerializer` 家</u>族/`Options.setTranslator`      |

由此推出两条设计红线，本方案逐条对齐：

- **R1 自洽优先**：自己写出的文件，必须能一字不差地读回来（含特殊字符、换行、反斜杠、含 `.` 的键）。
- **R2 失败必须原子且可见**：读坏或写坏的代价不能是"静默丢配置"，出错必须带位置信息。

而现状（2026-09-27 审核报告）在 R1/R2 上都破了：H-1/H-2/H-3/H-4 破 R1，H-6 破 R2。

## 2. 范围

**本次做**

1. 把"读文本"从"整行 trim + 前后缀字符串猜测"重构成**词法层 + 语法层**的分层结构。
2. 用该结构一次性消除 H-1（注释被当正文）、H-2（写出的换行读不回来）、H-3（反转义不可逆）、H-4（一行式 `k = [1,2]` 静默变空集）。
3. 用"先构建、后整体替换"消除 H-6（读坏 → 内存半截 → 下次保存抹掉原文件）。
4. 顺带处理零成本、零争议的 M 级项（M-1/M-3/M-5/M-7/M-9/M-11）与全部 `-Xlint:all` 告警（L-1）。

## 3. 分层架构

```
                 ┌──────────────────────────────────────────────┐
   文本  ───────▶ │ L1 lexer   Lexer / Token / TokenType         │ 字符流 → 记号流
                 │            「下一个记号是什么、在哪一行哪一列」 │ 只做边界判断，不做结构判断
                 └───────────────────┬──────────────────────────┘
                                     │ Token 序列
                 ┌───────────────────▼──────────────────────────┐
                 │ L2 parser  Parser / ParseException           │ 记号流 → 结点树
                 │            递归下降，错误带 文件:行:列         │ 不产生中间 AST
                 └───────────────────┬──────────────────────────┘
                                     │ 构建
   ┌─────────────────────────────────▼──────────────────────────┐
   │ L3 node    Node 模型 + 写出 + 寻址 + 选项                     │
   │   NodeBase / NodeList / NodeMap / FileNode（结点树、写出）     │
   │   Paths（寻址） / Options（装配） / Setting（绑定声明）         │
   └───────────┬────────────────────────────────▲───────────────┘
               │ 结点树                          │ 结点树
   ┌───────────▼────────────────────────────────┴───────────────┐
   │ L4 serializer  TypeSerializer 家族：Java 对象 ⇄ 结点          │
   └────────────────────────────────────────────────────────────┘
                                     ▲
   ┌─────────────────────────────────┴──────────────────────────┐
   │ L0 util    Strings（引号/转义唯一实现） / Reflects / Bounds   │
   └────────────────────────────────────────────────────────────┘
```

**依赖方向严格单向**：`L1 → L0`，`L2 → L1 + L3`，`L3 读取入口 → L2`，`L4 → L3 + L0`。  
`L0/L1/L2` 不知道"配置项""注解""序列化器"的存在，只处理文本与记号。

### 关键取舍：AST 就是 Node 树

不额外定义一套 AST 再"翻译"成 `Node` 树——**`Node` 树本身就是这门口的抽象语法树**。  
`Parser` 直接产出 `NodeMap / NodeList / NodeBase`。  
省掉一次深拷贝与一次整树遍历，也让"解析结果"和"运行时数据"天然是同一个东西（代码量、内存、GC 压力都更低）。这是"效率与简洁兼顾"在架构层的主要落点。

### 新增/变更的包职责

| 层  | 包                               | 类型                                    | 职责                                                   | 输入 → 输出                                    |
| -- | ------------------------------- | ------------------------------------- | ---------------------------------------------------- | ------------------------------------------ |
| L1 | `org.soraworld.hocon.lexer`     | `TokenType`(enum) / `Token` / `Lexer` | 单遍扫描字符，引号感知，产出带行列号的记号                                | `String`/`Reader` → `Token` 迭代             |
| L2 | `org.soraworld.hocon.parser`    | `Parser`                              | 递归下降，构建结点树；错误抛 `ParseException`                      | `Lexer` + `Options` → `NodeMap`/`NodeList` |
| L0 | `org.soraworld.hocon.exception` | `ParseException`                      | 带 `file/line/column` 的受检异常（`extends HoconException`） | —                                          |
| L0 | `org.soraworld.hocon.util`      | `Strings`                             | 引号判定与转义编解码的**唯一实现**                                  | `String` ⇄ `String`                        |

## 4. 数据流

**写出**：`Java 对象 ──(serializer)──▶ 结点树 ──(writeValue)──▶ 文本`  
结点写出时，键走 `Strings.quoteKey`（含 `.` 必加引号），值走 `Strings.quote`。

**读入**：`文本 ──(Lexer)──▶ 记号流 ──(Parser)──▶ 结点树 ──(serializer)──▶ Java 对象`  
读取入口只有两个，都遵循"**先构建、后整体替换**"：

```java
// NodeMap.readValue
NodeMap parsed = Parser.parseRoot(Lexer.readAll(reader), null, options, keepComments, null);
replaceValue(parsed.value);          // 只有解析全程成功才会执行这一行

// FileNode.load
NodeMap parsed = Parser.parseRoot(..., file.getPath(), options, keepComments, parsedHeads);
replaceValue(parsed.value);          // 失败则抛异常，this 原样不动，磁盘文件不受影响
setHeads(parsedHeads);
```

这就是 H-6 的根治：**解析失败不可能污染内存中的旧值**，因此"下一次 save 抹掉文件"的链条被切断；  
`load(backup)` 的 `backup` 参数随之变成 no-op（保留签名兼容），失败改为**抛出**而不是静默吞掉。

## 5. 文法（本次支持的范围）

```ebnf
root    ::= (entry | comment)* EOF
entry   ::= key ( '=' value | map )
key     ::= STRING | BARE                 (* 引号键=字面键；裸键内的 '.' 展开为层级 *)
value   ::= map | list | scalar
map     ::= '{' ( (entry | comment) (',' | NEWLINE)* )* '}'
list    ::= '[' ( (value | comment) (',' | NEWLINE)* )* ']'
scalar  ::= STRING | BARE
comment ::= ('#' | '//') 到行尾
head    ::= '#!' 到行尾                      (* 仅文件开头、首个条目之前算文件头 *)
BARE    ::= 直到 [空白 " { } [ ] = , #] 为止的连续字符
STRING  ::= '"' 转义感知扫描 '"'              (* 内容交给 Strings.unquote 解码 *)
```

**新语法相对旧实现的能力变化**

| 写法                          | 旧行为                                      | 新行为                                                           |
| --------------------------- | ---------------------------------------- | ------------------------------------------------------------- |
| `# 注释` / `#! 头`             | 注释行被当正文再解析一次 → 幻影键或越界崩溃（H-1）             | 统一由词法层产出 `COMMENT`/`HEAD` 记号                                  |
| `k = [1, 2, 3]`             | 静默得到**空** `NodeList`（H-4）                | 正常解析出 3 个元素                                                   |
| `k = {a = 1}`               | 静默得到空 `NodeMap` 且键名变成 `"k ="`（H-4）       | 正常解析，键名 `k`                                                   |
| `k = {}`                    | 键名 `"k ="`（P21）                          | 键名 `k`                                                        |
| `k {` … `}`                 | 正常                                       | 正常（`k { }` 与 `k = { }` 等价）                                    |
| `a.b = 1`                   | 键名字面为 `a.b`，与 `Paths` 寻址不一致（M-2）         | 展开为 `a` → `b` 两层，与 `Paths` 一致                                 |
| `key = 值` 值内含换行/反斜杠/控制字符    | 写出不加引号 → 读回崩溃或变形（H-2/H-3）                | 写出加引号并按对易表转义，读回严格等值                                           |
| 无法解析的行（`GARBAGE`、`= 2`、`{`） | `StringIndexOutOfBoundsException`（无位置信息） | `ParseException`，消息形如 `conf/xx.conf:7:3 键 'x' 之后缺少 '=' 或 '{'` |

## 6. 关键设计决策

| #   | 决策                                                                           | 理由                                                                                    | 对应问题            |
| --- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- | --------------- |
| D1  | **引号感知下沉到 `Lexer`**，转义表在 `Strings` 里只有一份                                     | 读侧（词法）与写侧（`quote`）共用同一张表，"减 1 取子串"式的越界判断从根上消失                                         | H-1 / H-2 / H-3 |
| D2  | **键与值分开的引号规则**：值不需要为 `.` 加引号，键需要                                             | `key3 = 123.456` 这类可读性保持不变；含点键得到 `"a.b"` 从而能字面往返                                      | M-1 / M-2       |
| D3  | **裸键按 `.` 展开层级，引号键按字面**                                                      | 与 `Paths` 的寻址口径统一；引号成为"我要一个字面键"的显式逃生口                                                 | M-2             |
| D4  | **先构建、后整体替换**                                                                | 解析是"全成或不动"，非法输入不可能留下半截状态                                                              | H-6             |
| D5  | **保存走同目录临时文件 + `ATOMIC_MOVE`**                                               | 进程崩溃、磁盘满、写入异常都不会留下半截配置；`ATOMIC_MOVE` 不支持时回退 `REPLACE_EXISTING`                        | M-5             |
| D6  | **删除 `Field.modifiers` 与常量池/lambda 解析这一整套反射黑魔法**                             | 这是 JDK 16+ 必崩（H-5）与第三方许可（M-11）两个问题的共同根源；删掉后 JDK 8/17/21 行为一致                          | H-5 / M-11      |
| D7  | **`Paths` 改为不可变值对象**（`next()/revert()/copy()` 返回新实例）                         | 公开 API 不再消耗调用方传入的对象；`M-7` 的"复用同一个 Paths 就出错"消失                                        | M-7             |
| D8  | **`Node` 树即 AST**，不做中间层                                                      | 少一次深拷贝与整树遍历，代码量更小                                                                     | I1（轻量）          |
| D9  | **`NodeBase/FileNode` 去掉 `implements Serializable` 与反射改值**，改用 `replaceValue` | 该序列化契约本就不可用（P9/`InvalidClassException`）；去掉后翻译与加载回滚不再依赖 `setAccessible` 打自己类的 final 字段 | M-6 / I-3       |
| D10 | **`List/MapSerializer` 在缺序列化器时抛 `SerializerException`**，而不是继续解引用 null        | NPE 冒到业务层是"看不懂的崩溃"，明确异常才能被现有 `catch (HoconException)` 兜住                              | M-3             |
| D11 | **序列化器选"最具体"改为显式比较**，不再依赖 `TreeSet` + 非法全序                                   | 选型不再依赖注册顺序；`compareTo`/`equals` 口径一致                                                  | M-8 / M-9       |

## 9. 验收方式

零依赖约束下不引入 JUnit，采用**无依赖自检程序 + Gradle 任务**：

```groovy
// build.gradle 追加
tasks.register('verify', JavaExec) {
    group = 'verification'
    mainClass = 'org.soraworld.hocon.HoconVerify'
    classpath = sourceSets.test.runtimeClasspath
}
```

`src/test/java/org/soraworld/hocon/HoconVerify.java` 用 `main` 跑断言，逐节捕获异常并汇总。用例清单（直接覆盖审核报告里已复现的每一个现象）：

| 组 | 用例 | 期望 |
|---|---|---|
| A 往返 | 普通值 / 中文 / 含特殊字符 / 含空格 / 空串 / `"null"` / 多层嵌套 / 列表套列表 / 列表套映射 | 保存 → 读回 → 逐键等值 |
| B 转义 | 含 `\n`、`\r`、`\t`、`\b`、BEL(0x07)、`\`、`C:\new\test`、正则串 | `unquote(quote(x)).equals(x)`，且文件往返等值（对应 P4/P5/P23） |
| C 注释 | `#` 单行 / `#!` 文件头 / 列表体内注释 / 映射体内注释；`keepComments` 两态 | 注释归位正确、条数稳定；**多轮 load+save 不再增长**（对应 P1/P2/P3/P10） |
| D 一行式 | `k = [1,2,3]` / `k = {a=1}` / `k = {}` / `k { }` / `k = 1` | 内容与键名全部正确（对应 P6/P21） |
| E 失败原子性 | 文件中间插入 `GARBAGE` 后 `load(true,true)`；断言"内存旧值不变 + 磁盘字节数不变" | 抛带行列号的 `ParseException`（对应 P16/P17/P25） |
| F 含点键 | `Map<String,Integer>` 键为 `example.com` / `app.log` / `1.2.3` | 写出加引号、读回键与值都正确（对应 P8/M-1） |
| G 绑定 | `@Setting` 字段的 `extract`/`modify`（含 `List`/`Set`/`Map`/`Enum`/嵌套对象/静态字段） | 与旧版行为一致（对应 P11/P12/P14/P15/P19/P20/P22） |

| I 跨 JDK | 在 JDK 8 与 JDK 21 各跑一遍全部用例 | 结果一致、且**任何一次构造 `FileNode` 都不再打印 `NoSuchFieldException: modifiers`** |

判定标准：全部通过 + `-Xlint:all` 零告警 + JDK 8/21 结果一致。
